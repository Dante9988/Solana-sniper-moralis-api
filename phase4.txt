## 1. Canonical chain registry

Support identity definitions only for:

```ts
type SupportedChain =
  | "SOLANA"
  | "ETHEREUM"
  | "BNB_SMART_CHAIN";
```

Registry values:

* Solana mainnet:

  * internal chain ID: `solana-mainnet`
  * address format: Solana public key
* Ethereum mainnet:

  * chain ID: `1`
  * address format: EVM
* BNB Smart Chain mainnet:

  * chain ID: `56`
  * address format: EVM

Do not add live Ethereum or BNB RPC/API calls.

Use a centralized immutable registry rather than scattered constants.

## 2. Canonical asset identity

Implement a shape equivalent to:

```ts
interface AssetIdentity {
  id?: string;
  chain: SupportedChain;
  chainId: string;
  address: string;
  normalizedAddress: string;
  symbol?: string;
  name?: string;
}
```

Rules:

* Canonical database identity is `chainId + normalizedAddress`.
* Solana addresses remain case-sensitive.
* Validate Solana addresses using `PublicKey`.
* For valid Solana input, canonicalize through the public key representation without lowercasing.
* EVM addresses must be exactly `0x` plus 40 hexadecimal characters.
* EVM `normalizedAddress` must be lowercase.
* Preserve the supplied address separately for display when useful.
* The same EVM address on Ethereum and BNB Chain must produce different canonical identities.
* Symbol and name are mutable metadata and must never determine identity.
* Do not merge assets by symbol, name, website, or social links.
* Do not silently default ambiguous EVM input to Ethereum.
* Unsupported chains must return an explicit error result.

No new EVM library is necessary unless the existing dependency graph already provides a suitable validator. Strict hexadecimal validation and lowercase normalization are sufficient for Phase 4.

Do not implement EIP-55 checksum generation in this phase.

## 3. Asset resolution API

Create an explicit resolution input and result.

Use behavior equivalent to:

```ts
interface AssetResolutionInput {
  address: string;
  chain?: SupportedChain;
}

type AssetResolutionResult =
  | {
      status: "RESOLVED";
      asset: AssetIdentity;
    }
  | {
      status: "AMBIGUOUS_CHAIN";
      inputAddress: string;
      candidateChains: SupportedChain[];
    }
  | {
      status: "INVALID_ADDRESS";
      reason: string;
    }
  | {
      status: "UNSUPPORTED_CHAIN";
      reason: string;
    };
```

Required behavior:

* Valid Solana address without a chain hint may resolve to Solana if it unambiguously validates as a Solana public key.
* A bare valid `0x` address without a chain hint must return `AMBIGUOUS_CHAIN`.
* Its candidates must include Ethereum and BNB Smart Chain.
* A valid EVM address plus Ethereum resolves to chain ID `1`.
* A valid EVM address plus BNB Smart Chain resolves to chain ID `56`.
* A Solana address with an EVM chain hint is invalid.
* An EVM address with a Solana chain hint is invalid.
* Whitespace may be trimmed at the input boundary.
* Empty, malformed, or unsupported input must not produce a fabricated asset.
* Expected user-input errors should be returned as result values, not uncontrolled exceptions.

## 5. Market-observation contract

Implement a provider-neutral shape equivalent to:

```ts
interface MarketObservation {
  asset: AssetIdentity;
  observationKey: string;
  observedAt: Date;
  source: string;
  provider?: string;
  priceUsd?: number;
  estimatedBuyPriceUsd?: number;
  estimatedSellPriceUsd?: number;
  liquidityUsd?: number;
  marketCapUsd?: number;
  fdvUsd?: number;
  volume24hUsd?: number;
  rawPayload?: unknown;
}
```

Rules:

* `observationKey` must be stable and caller-supplied or deterministically constructed from stable source evidence.
* Do not use `observedAt` as the sole idempotency key.
* Missing numerical data remains `undefined`/`null`, never zero.
* Never use a hardcoded SOL/USD value as research evidence.
* Never convert provider failure into zero liquidity, zero price, or zero volume.
* Validate that supplied numerical values are finite and non-negative where applicable.
* Record both `source` and `observedAt`.
* Keep displayed market price separate from estimated executable buy and sell prices.
* Preserve raw provider evidence when supplied.
* Constructors/adapters must be pure and must not perform HTTP, RPC, database, scheduler, wallet, or transaction operations.

Do not refactor the existing trackers or provider fallback order in this phase.

## 6. PostgreSQL models

Add only additive Prisma models and an additive migration.

Use repository naming conventions, but implement a relational structure equivalent to:

```prisma
model Asset {
  id                String   @id @default(cuid())
  chain             String
  chainId           String
  address           String
  normalizedAddress String
  symbol            String?
  name              String?
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  observations AssetObservation[]

  @@unique([chainId, normalizedAddress])
  @@index([chain])
  @@index([normalizedAddress])
}

model AssetObservation {
  id             String   @id @default(cuid())
  assetId        String
  type           String
  source         String
  observationKey String
  observedAt     DateTime
  provider       String?

  priceUsd             Decimal?
  estimatedBuyPriceUsd Decimal?
  estimatedSellPriceUsd Decimal?
  liquidityUsd         Decimal?
  marketCapUsd         Decimal?
  fdvUsd               Decimal?
  volume24hUsd         Decimal?

  rawPayload Json?
  createdAt  DateTime @default(now())

  asset Asset @relation(fields: [assetId], references: [id], onDelete: Cascade)

  @@unique([assetId, source, observationKey])
  @@index([assetId, observedAt])
  @@index([type, observedAt])
  @@index([source, observedAt])
}
```

Adjust scalar types only when required by the existing Prisma/PostgreSQL conventions.

Critical idempotency rule:

```text
UNIQUE(assetId, source, observationKey)
```

Do not use this weaker design:

```text
UNIQUE(assetId, type, source, observedAt)
```

Two legitimate observations can share a timestamp, and retry timestamps may differ. The stable observation key must own deduplication.

Do not:

* modify existing intelligence models destructively
* add foreign keys to all legacy tables
* migrate legacy SQLite holdings
* migrate `TokenAlert`
* add listener dual writes
* run destructive migrations
* apply the migration to an unknown/live database

Generate or hand-write the additive SQL using Prisma 6.5-compatible tooling and review it manually.

The SQL must contain only additive enum/table/index/constraint operations required by Phase 4.
